# UX audit and proposal — 2026-11-05

Proposal for review, not an implemented interface. Reviewed the current uncommitted setup fixes, console output, command launchers and the user's fresh KoboldCpp setup transcripts. Source owners are [setup presentation](../../internal/setup/wizard.go), [setup planning/install](../../internal/setup/setup.go), [application dispatch](../../internal/app/run.go), [update workflow](../../internal/updater/workflow.go) and [launcher templates](../../scripts/launchers).

## Assessment

The common setup path requires five decisions: container, profile, runtime, snapshot paths and installation confirmation. The program already knows enough to answer several of these, but asks the user to confirm them independently. Repeating a folder explanation cannot fix that interaction model.

The target experience should be **select an application folder, review the detected setup, confirm**. If the executable is already in a validated container, folder selection can also be skipped. Unusual layouts need an escape route, not mandatory questions for everyone.

Keep a plain console for this increment. A small amount of layout and consistent controls will improve the flow without a GUI toolkit, web server, full-screen terminal framework or scripting requirement. Evaluate a native GUI later if real use still shows that folder selection is the dominant problem.

## Proposed setup flow

### 1. Resolve the application

On launch without configuration:

- If the executable is under `util/portable-update`, derive the possible outer folder and validate it. Use it automatically only when it resolves to one valid supported installation.
- Otherwise ask: `Application folder — paste or drag it here:`. Accept a folder or a supported executable path. The review shows the resulting outer folder and application-files folder.
- Use bounded detection: the selected location, recognized parent relationship, supported default paths and immediate child directories. Do not recursively search drives or choose the first result of an ambiguous search. Validate the selected package/portable files before calling it detected.
- One validated application goes directly to review. Multiple candidates show only those candidates with their paths. No match leads to a short manual selection and location flow, preserving the entered path.

Friendly application names belong in adapter data, with the existing identifier as a compatibility fallback for custom definitions. No application-name switches should be added to Go presentation logic.

### 2. Review and confirm

**Proposed console output, not a screenshot of an implemented UI:**

```text
Portable Updater — Set up KoboldCpp

Application folder  F:\Projects\ai\koboldcpp
Application files   extracted\
Extra backups       None selected

Create updater configuration and update/restore shortcuts.
Existing matching updater files will be reused.

Enter  Set up updater
E      Edit choices
Q      Cancel
```

This replaces profile, runtime and backup questions when the application is unambiguous. It still requires an explicit confirmation before writing. Confirmation configures the updater and does not immediately download or replace the application.

Show detected backup selections as actual paths, or a count with an accessible list. `None selected` means no additional pre-update backup copies are configured; it must not be described as proof that no personal data exists. The updater does not discover every application's data configuration.

### 3. Edit only when needed

Edit opens a small menu: application folder, application choice/files location, extra backup folders, release channel, and Back to review. Preservation details can be read there. Existing validated values remain when moving between screens.

For extra backups:

```text
Extra backups before each update
No files or folders selected.

A      Add a file or folder
Enter  Done
B      Back
```

After Add, accept a pasted/dragged path and show its normalized selection. Offer Remove only when there are selections. Validate paths and overlaps immediately; explain that these are extra copies, separate from runtime rollback. Do not automatically include large model or game libraries.

### 4. Finish with the next action

```text
KoboldCpp updater is ready.

To update:   double-click updater-update.cmd
To restore:  double-click updater-rollback.cmd
```

If setup is launched for a configured container, show its status and the same next action. Do not overwrite its configuration as a side effect of opening setup. Restore instructions should note that a previous update must exist when the user tries that action.

## Update and restore presentation

Normal configured execution remains direct: no new menu or confirmation before every update. Keep the existing root command files and power-user flags.

Console status should cover checking, obtaining the package, preparing backups/settings, and installing. Show byte progress for downloads when available. Do not display an invented total percentage for extraction or filesystem swaps. A no-change check ends promptly with a single clear outcome.

Use a concrete release version only when it is known. A moving tag called `latest` is not a semantic version. Success states that the application was updated and that a previous version is available only when the retained rollback copy exists. The details log can retain hashes, receipt failures, provider responses and cache decisions.

Errors should answer three questions: what happened, whether replacement occurred, and what to do next. Derive the state statement from the transaction result; do not print `nothing changed` for every failure. Example for a failed download before replacement:

```text
Could not download the update.
The installed application was not replaced.

Check the connection and run updater-update.cmd again.
Details: ...\tmp\portable-update\update.log
```

Keep errors visible through the launcher. This increment does not need a dashboard, update scheduler or collection browser. Plain labels, spacing and consistent controls are sufficient; optional color must not carry meaning on its own or leak into logs/redirected output.

## Implementation boundary

1. Separate discovery and the reviewable setup plan from console prompts. Existing `Prepare`/`Install` remain responsible for validation and non-overwriting installation; the UI does not duplicate their policy.
2. Replace the linear questionnaire with a few explicit screens: locate, disambiguate, review, edit and result. Keep the state local and testable with input/output streams.
3. Consolidate user-facing labels and error presentation. Feed ordinary progress and detailed logs separately with the smallest change that preserves current transaction behavior; do not build a general event framework.
4. Update only affected documentation and use actual recordings of the implemented flow. The mock console above must not be published as a shipped interface before it exists.

No downloader, rollback algorithm or provider redesign is required for this UX increment. No changes to user data locations or existing runtime launching are part of it.

## Acceptance checks

- A standalone executable plus a recognized application folder requires folder selection and one explicit confirmation; there are no profile, runtime or backup prompts in that default path.
- An executable already in a recognized container without configuration goes directly to review and needs one confirmation.
- Fresh setup works with only the executable in its final directory and with identical existing launchers. Conflicting files remain protected.
- Outer folder, application-files folder and executable selections resolve to the same plan for a supported layout.
- Multiple installations never cause a silent first-match choice; an unknown/custom layout remains configurable.
- No raw comma-separated backup list, `-` sentinel, preservation list or internal profile ID is required on the common path.
- Edit/Back retains inputs. Invalid responses can be corrected locally. Cancel/EOF produces no setup writes; returned installation errors remove only files created by that attempt.
- Existing config, invalid config and orphaned transaction state each have a distinct, accurate result.
- Setup completion, no update needed, successful update, failed download, active-process block, failed swap and restore each have a concise outcome and an actionable next step.
- Redirected output remains readable; required behavior does not depend on terminal colors or cursor controls.

Verify with scripted console tests and an extracted-binary smoke test, then repeat the fresh KoboldCpp flow manually. Success means that the user completes it without external instructions about what to type, not just that tests can feed the expected answers.
