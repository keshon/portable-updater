# Application audit — 2026-11-05

Historical review of the uncommitted working tree based on `0e7327700ad05fe91cc3ddad9f97ee242de2d030`. It covers product scope, architecture, configuration, download and installation failures, Windows integration, distribution, tests and documentation. This is a source review with local verification, not an independent security assessment or certification of supported applications.

## Assessment

The useful product is a Windows tool that updates an **existing portable runtime**, preserving explicitly configured state and retaining one automatic rollback. The separation between release discovery, downloading and filesystem transactions is appropriate. Adapters, examples and embedded setup profiles now share one catalog. A Go executable and two command launchers are a reasonable distribution for this audience.

The implementation had real correctness defects, especially around failed updates retaining rollback. Those warranted fixes before release. The changes below address reproduced cases, rather than treating a successful package download as proof that the whole updater works.

The current result is suitable for a technical preview used with disposable checks and separate backups. Wider promotion should wait for packaged CLI checks in CI and a clearer subprocess cancellation/recovery contract. The console setup helps collection owners; it does not discover every application's data configuration or make an arbitrary Windows program portable. Positioning should retain that boundary.

## Remaining findings and priorities

### P2 — Direct-process timeout does not own the full process tree

[Executable unpacking](../../internal/updater/package.go) uses `exec.CommandContext`. Cancellation terminates the direct child; it does not guarantee termination of descendants. An unpacker is also upstream code running with the user's permissions, regardless of its working directory or checksum.

Before advertising general self-extractor support, implement and test Windows process-tree ownership, likely with a Job Object, or retain the explicitly limited contract. Test a helper that spawns a child and attempts a delayed write after cancellation. Avoid implying that publisher integrity provides sandboxing.

### P2 — Packaged CLI behavior is verified locally, not in CI

Core tests exercise filesystem faults, but `internal/app` and the command entry point have no dedicated automated tests. The release archive's version/help/setup/cancel checks were performed locally. Release CI tests source and creates the ZIP without replaying that first-run scenario.

Add a packaged smoke check using a synthetic Windows runtime fixture: extract the archive into a path with spaces, check version/help, cancel setup, install, check unchanged original files, and reject a duplicate installation. This provides more useful assurance than pursuing a coverage percentage. Keep live upstream availability outside mandatory CI tests.

### P2 — Setup cannot infer the application's complete data policy

[Setup](../../internal/setup/setup.go) checks an entry point, required files and example paths. It does not parse each application's configured data locations or registry behavior. An omitted snapshot path remains omitted; an existing portable marker does not prove that every write stays in the container.

Keep the review step explicit and the current existing-installation boundary visible. Future detection should be evidence-backed and application-specific declarative data where possible. Native Windows profile/registry isolation and Linux runtime verification remain outside this updater audit.

### P2 — State validation is repeated and has gaps

The JSON schema, loader and setup preview express overlapping rules. Snapshot paths are checked against updater storage, but duplicate or nested snapshot roots are not rejected together. Such roots can double-count size or collide when copying their backup files, producing a late failure. Some schema constraints are editing aids rather than enforced runtime rules.

Consolidate pure configuration/path-policy validation and reuse it for preview and loading. Reject duplicate/nested snapshot roots before writes. Do not introduce a general schema execution framework solely to avoid a small shared validator.

### P2 — Retention and crash behavior need bounded operational contracts

Previous/rejected runtimes, snapshots, defaults and cached packages accumulate. There is no automatic retention or disk-space estimate. Manual cleanup is documented, but deleting the workspace also removes rollback material. This limits a long-term unattended-use claim.

Normal setup errors clean up owned files; process termination may leave a partial setup that the next attempt refuses. Swap recovery recognizes directory layouts, but journaling does not establish power-loss durability. Prioritize a recoverable setup marker and a narrowly specified retention policy that protects every path referenced by the active journal. Do not add broad recursive cleanup or claim universal crash recovery.

### P3 — Reusable adapter defaults include collection-specific settings

The [Dolphin adapter](../../adapters/dolphin-windows.json) preserves `ReShadeMGS4_1.ini`, a collection-specific filename. Other preservation lists also include optional local additions. These are declarative, but they blur a reusable application profile and one owner's configuration.

Separate canonical defaults from per-container optional preservation when that policy is designed. Preserve existing operator settings during migration; removing an unfamiliar preservation entry is not a safe cleanup.

### P3 — Distribution and service limits remain visible

The candidate executable is unsigned, and this review did not test a clean Windows VM or multiple endpoint-security products. GitHub metadata requests use anonymous service access, so many independent containers may encounter rate limits. The custom resumable range downloader has substantial complexity and should keep its current focused scope until more failure evidence justifies additions.

Document actual failures and add regression checks for them. Avoid expanding into a package manager, installer, background service, GUI framework or multi-platform runtime before the Windows update path has broader operational evidence.

## Recommended next increment

1. Add the extracted-ZIP smoke check to CI and cover CLI dispatch errors.
2. Establish process-tree cancellation and partial-setup recovery behavior with fault tests.
3. Share input validation and reject overlapping snapshot roots before setup/install work.
4. Design bounded retention separately, with an explicit rule for keeping active rollback material.

Keep the public promise narrow: update an already portable runtime according to reviewable adapter policy. RPCS3, Dolphin and KoboldCpp now follow that policy model; they do not require application names or endpoints in updater behavior.
